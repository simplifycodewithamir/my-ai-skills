01 · Environment

Why WSL instead of Windows + Visual Studio

Previously: build in Visual Studio, launch locally, test with Postman — never actually running as the container that ships to production. Moving into WSL Ubuntu closes that gap, because the dev loop now matches the deploy target.

Old — Windows / Visual Studio
New — WSL Ubuntu / VS Code
  • Run via dotnet run / IIS Express, not a container
  • Never touching the Linux toolchain the pipeline actually uses
  • Manual Postman checks, no local Docker parity
  • Same Linux filesystem the CI/CD pipeline builds from
  • Can run the app as an actual Docker image locally — same shape as prod
  • VS Code attaches via Remote-WSL — one real shell, no cross-filesystem lag
Gotcha
  • Opening a WSL folder through \\wsl$\... from Windows Explorer connects over a network share — slower, and can cause file-permission / line-ending issues.
  • sudo mkdir for your own folders leaves them root-owned — causes permission friction with git and VS Code later.
Do instead
  • From inside a WSL terminal: cd into the repo, then code . — opens VS Code already attached in Remote-WSL mode.
  • Fix accidental root ownership with sudo chown -R $USER:$USER ~/.claude.
02 · Two different memory mechanisms

CLAUDE.md vs. Skills — not the same tool

CLAUDE.md is location-triggered: whatever file sits at that level loads in full, always, whether relevant or not. A Skill is task-triggered: only its name + one-line description sit in context by default; the full content loads only when the task actually matches.

CLAUDE.md
Skills
  • Loads in full, based on where you are (global, repo, subfolder)
  • One flat file — simple, but grows unwieldy
  • Good for: working-style rules, repo-specific facts
  • Loads based on what task you're doing
  • Modular — one concern per skill, can bundle scripts/templates
  • Good for: reusable conventions across every repo

The three-level split in use here

~/.claude/CLAUDE.md

Global working style: run ahead without asking, stop only for destructive/ambiguous/costly changes, no flattery, concise, code over prose.

<repo>/CLAUDE.md

Repo-specific facts only — service name, ports, DB, deploy namespace. Points to the skills for conventions, never restates them.

Skills (6, symlinked from a repo)

The actual reusable conventions — production code, testing, CI/CD, frontend, git — single source of truth, edited once.

03 · What got built

Six skills, one router

Each skill states what to do and — just as important — what not to do, so conventions like "exceptions, not Result<T>" or "Testcontainers, not mocks" get enforced rather than just documented.

dotnet-stack

Aggregate router. Points to the right sub-skill(s) instead of dumping everything into context at once.

dotnet-production-code

Minimal APIs + endpoint groups, exceptions → ProblemDetails, TimeProvider, Serilog + OTel, resilience retries.

dotnet-testing

xUnit, test-first, Testcontainers over mocks, WebApplicationFactory over TestServer.

cicd-pipeline

GitHub Actions stages, self-hosted Artifactory promotion flow, separate k8s-deploy repo, AKS + Key Vault.

react-frontend

TypeScript, functional components only, query-library server state, accessibility floor, Tailwind.

git-workflow

Conventional Commits, no force-push to shared branches, no AI co-author.

Wiring them in — the reliable pattern

Symlinking the whole ~/.claude/skills folder has open, unresolved discovery bugs. Symlinking each skill folder inside a real parent directory is the pattern that actually works:

$ mkdir -p ~/.claude/skills $ ln -s ~/repos/my-ai-skills/dotnet-stack ~/.claude/skills/dotnet-stack $ ln -s ~/repos/my-ai-skills/dotnet-production-code ~/.claude/skills/dotnet-production-code # ...repeat per skill, then verify: $ claude > /skills # all six should show "On"
Do
  • Repo is the source of truth — edit there, symlink reflects it instantly, no restart needed.
  • Skill body edits are picked up live by a running Claude Code session.
Don't
  • Don't symlink ~/.claude/skills itself — known regression, skills silently fail to be discovered.
  • Don't duplicate a convention in both a project CLAUDE.md and a skill — it will drift.
04 · Reviewing what Claude Code did

No Beyond Compare needed — it's built in

VS Code's Source Control panel gives the same side-by-side diff as Beyond Compare, GitHub Desktop, or Visual Studio's diff tool — and it works natively over the Remote-WSL connection.

$ git status # confirm what changed $ git diff # quick inline read in the terminal # — or — Ctrl+Shift+G → Source Control panel → click a file for a visual diff
